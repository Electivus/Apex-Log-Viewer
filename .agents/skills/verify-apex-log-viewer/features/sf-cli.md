# sf electivus CLI plugin

The `sf electivus` Salesforce CLI plugin exposes the same core as the extension, for terminals and agents. It syncs Apex logs into the shared `apexlogs/` store, reports sync state, lists, reads and triages logs, manages trace flags and debug levels behind a preview, reads and captures custom logs, and installs the bundled Agent Skills.

## Sub-features

- `cli-log-sync` (`log sync`) downloads new logs into `apexlogs/orgs/<safe org username>/logs/<YYYY-MM-DD>/…` and advances `apexlogs/.alv/sync-state.json`. It also writes `apexlogs/.alv/version.json` and `apexlogs/orgs/<safe org username>/org.json`, and appends `apexlogs/` to the workspace `.gitignore` when that file exists. `--force-full` rescans every org log, and `--concurrency` (1 to 8, default 6) bounds the downloads. A log that `log read` already cached under `unknown-date/` counts as `cached` and is not downloaded again. `status` is `success` or `partial`, and a `partial` sync still exits 0.
- `cli-log-status` (`log status`) reads the local state only: `hasState`, `logCount`, the counts of the last sync, and, once a sync wrote state, `lastSyncedLogId`, `lastSyncedStartTime` and `orgLogsRoot`.
- `cli-log-read` covers `log list` (`--limit`, `--offset`, or `--before-id` with `--before-start-time`), `log read` (`--max-bytes`), `log resolve`, `log triage` and `log delete`. `log delete` also takes `--scope mine|all`, `--limit` and `--ids-file`, and deletes org records only: local copies stay.
- `cli-trace-flag` covers `trace-flag status`, `apply` and `remove`. Each takes `--log-type DEVELOPER_LOG|USER_DEBUG` (default `DEVELOPER_LOG`) and echoes `result.logType`. Without a target flag the target is the current user; `--user-id`, `--current-user`, `--automated-process` and `--platform-integration` are mutually exclusive. `status` also reports `otherLogType` and a warning when the other type's flag matters. `apply` needs `--debug-level`, takes `--ttl-minutes` (1 to 1440, default 30) and updates the newest flag of that type on the target, even an expired one, instead of adding another. `remove` deletes every flag of the chosen type on the target, expired ones included.
- `cli-debug-level` covers `debug-level list`, `get` (`--id` or `--developer-name`), `create`, `update` and `delete`. `create` defaults to `en_US`, a label equal to the developer name, `ApexCode` and `System` at `DEBUG` and every other category at `INFO`; `update` sends only the fields you pass.
- `cli-custom-log` covers `custom-log sources`, `list`, `get`, `entry` and `capture` (see [custom-logs.md](./custom-logs.md)). `list --entries` lists the entry records of a `transactions` source, each with its transaction in `log`, and `sources` reports `entryCapabilities` for it.
- `cli-org-user-tooling` covers `org list`, `org resolve`, `user search`, `tooling query` and `tooling get` (read-only). `tooling get --path` takes a path that starts with `/`, resolved against the org's data API (`/tooling/sobjects/ApexLog/<id>` reads `/services/data/v<latest>/tooling/…`), a full `/services/data/vXX.X/…` path, or an absolute URL on the org's own instance.
- `cli-doctor` (`doctor`) checks the runtime, the org auth and the local log store.
- `cli-skill-install` (`skill install --agent <a>|--skills-dir <dir> [--skill <name>…|--all] [--global] [--dry-run] [--force]`) copies the bundled Agent Skills. Without `--agent` or `--skills-dir` it prompts in a terminal and fails under `--json` or without a TTY.

## How to get to it (user POV)

- Run `sf electivus <topic> <command> [--json]` (`sf electivus doctor` has no topic) in an SFDX project, after installing `@electivus/plugin-electivus`. `--target-org <alias>` is optional when the project's `.sf/config.json` sets `target-org`.
- In this repo, `node packages/sf-plugin/bin/run.js electivus …` runs the local build without `sf`. `sf plugins link packages/sf-plugin` makes the real `sf` load the local build. The verify session wraps both.

## Driving it with verify steps

Preconditions:

- Baseline from `README.md`. The plugin is built (`start` runs `pnpm run build`, which includes `build:sf-plugin`).

Shorthand: `S` is `node .agents/skills/verify-apex-log-viewer/scripts/verify.mjs sf --`, which runs `node packages/sf-plugin/bin/run.js electivus`. `SL` is `node .agents/skills/verify-apex-log-viewer/scripts/verify.mjs sf --linked --`, which runs the real `sf electivus` with the local build linked.

- **Real sf.** Use `SL` to prove a command the way a user runs it, through the `sf` on PATH. The first `SL` call of a session gives `sf` its own `SF_DATA_DIR`, `SF_CACHE_DIR` and `SF_CONFIG_DIR` under `output/verify/session/sf-cli/` and runs `sf plugins link packages/sf-plugin --no-install` there. That `sf` sees only the local build: the user's installed plugins stay hidden and untouched, and `sf plugins` outside the session still lists the user's own version. Org auth is shared, because it lives in `~/.sfdx`. `stop` deletes the directory and the link with it. Each call prints `Warning: Could not find typescript. Please ensure that typescript is a devDependency. Falling back to compiled source.` on stderr: `sf` then runs `packages/sf-plugin/lib`, the build. On 2026-11-13, `SL doctor`, `log sync`, `trace-flag apply` (preview), `custom-log list --entries` and `custom-log capture` matched `S`, in about 1 s per call.
- **Status after extension activity.** After the `logs-open-viewer` step and the Logs panel's background sync, `S log status --json` exits 0 with `result.hasState: true` and `lastSyncedLogId` set to the newest log that sync listed. This proves both surfaces share `sync-state.json`. Before either surface has synced this org in the workspace, `hasState` is `false` and `orgLogsRoot` and `lastSynced*` are absent.
- **Sync.** Seed a log, then run `S log sync --json`. It exits 0 with `result.status: "success"`, `downloaded ≥ 1`, `checkpointAdvanced: true` and `lastSyncedLogId` equal to the newest id. A second run returns `downloaded: 0, cached: 0` with `checkpointAdvanced: false` and the same `lastSyncedLogId`, because nothing newer was listed (while the checkpoint log still exists in the org; once it is deleted, an incremental sync rescans everything). `S log sync --force-full --json` counts the stored logs as `cached`.
- **Read back.** After `logs-open-viewer`, `S log read --log-id <session.seeded.logId> --json` returns the dated path the panel's sync wrote, which proves the CLI reads the shared store. To prove a fetch from the org, read a log nothing has cached yet: run a step that returns `await h.seedLog()`, check `S log resolve --log-id <logId> --json` returns `cached: false`, then run `S log read --log-id <logId> --json`. The body contains the marker, and the log is now cached at `apexlogs/orgs/<safe org username>/logs/unknown-date/<logId>.log`. The panel's sync uses a dated folder instead, so the two layouts coexist. A panel refresh in between caches the log first, so read before you refresh.
- **Triage.** `S log triage --log-id <id from h.seedErrorLog()> --json` returns `result[0].summary` with `hasErrors: true`, `primaryReason: "Fatal exception"` and a `fatal_exception` reason at line 4.
- **Trace flags.** `S trace-flag status --json` reports the seeded flag: `logType: "DEVELOPER_LOG"`, `isActive: true`, `debugLevelName: "ALV_E2E"`. `S trace-flag apply --debug-level ALV_E2E --log-type USER_DEBUG --ttl-minutes 5 --json` previews `status: "success"` with `dryRun: true`; add `--yes` to write it (`createdCount: 1`, or `updatedCount: 1` when the user already had a `USER_DEBUG` flag, even an expired one). `S trace-flag status --log-type USER_DEBUG --json` then has `otherLogType: { logType: "DEVELOPER_LOG", isActive: true, … }` and `warnings[0]` `A DEVELOPER_LOG trace flag is also active on this target…`, the CLI side of the Debug Flags note. Finish with `S trace-flag remove --log-type USER_DEBUG --yes --json`, which leaves the seeded `DEVELOPER_LOG` flag alone. `S trace-flag status --automated-process --json` (or `--platform-integration`) gives `resolvedTargetCount` and `traceFlagIds` for a special target.
- **Debug levels.** `S debug-level create --developer-name ALV_VERIFY_CLI --system FINE --yes --json` creates the level in `en_US`, then `get --developer-name …`. `update --id <id> --apex-code FINEST --yes --json` changes only that field, which a Tooling read-back proves. Without `--yes`, both commands preview and fail on a value the org's restricted picklists reject, such as `--language Bogus` (`Master Language: bad value for restricted picklist field: Bogus. Allowed values: …`). Finish with `delete --id <id> --yes`.
- **Delete.** `S log delete --log-id <id> --json` previews (`dryRun: true`, `logIds`); `--yes` deletes (`deleted: 1`), and `S tooling query --soql "SELECT Id FROM ApexLog WHERE Id = '<id>'" --json` returns `totalSize: 0`. The cached copy stays, and `log resolve` still reports it.
- **Custom logs.** Map the `Account` fixture of [custom-logs.md](./custom-logs.md#driving-it-with-verify-steps) in the session workspace, then: `S custom-log sources --json` (`state: "ready"`, `shape: "entries"`, `entryCapabilities`); `S custom-log list --source alv-accounts --min-level ERROR --since 1h --payload-fields http.status --json` (only `Hot` rows, `payload.values` holding only `http.status`); `S custom-log get --source alv-accounts --log-id <row id> --json` (the entries of that `AccountNumber`, `apexLog.state: "linked"`); `S custom-log entry --source alv-accounts --entry-id <row id> --json` (`details[0].key: "BillingStreet"`, `rawPayload.state: "value"`). With two ready record sources, `list` without `--source` fails with `Several log sources are ready (…). Pass one with --source.`. Add the `alv-tx` source from the same file for `--entries`. Delete the token-tagged records at the end.
- **Capture.** `custom-log capture` needs a custom platform event, which only the `alv-events` org has. Pass `--target-org alv-events` from any session after mapping an `event` source in the session workspace; [custom-logs.md](./custom-logs.md#platform-event-sources) has the recipe and the refusals.
- **Other topics.** `S doctor --json` (`status: "ok"`, `orgAuth.ok`, `sf.message` counting the CLI's orgs, `cacheLayout.message` counting the org folders under `apexlogs/orgs` or `no apexlogs directory yet`, `workspaceRoot` = the session workspace; doctor never creates `apexlogs/`), `S org resolve --json` (`source: "alias"`), `S user search --query alv.debugflags --json`, `S tooling get --path /tooling/sobjects/ApexLog/<id> --json`, and from the session workspace `node <repo>/packages/sf-plugin/bin/run.js electivus skill install --skills-dir <scratch dir> --all --dry-run --json` (three skills, `status: "wouldInstall"`, nothing written).
- **Proof.** Each `S` call writes `cli-<YYYYMMDD-HHMMSS.mmm>-sf-<first two command words>.json` (the words before the first flag) (command, cwd, exit code, stdout, stderr) to the evidence directory, for example `…-sf-log-sync.json`, or `…-sf-doctor.json` for a one-word command. An `SL` call writes `…-sf-linked-<words>.json` with the command `sf electivus …`. stdout is exactly the command's stdout; the `verify: exit <n>; recorded <file>` line goes to stderr.

## Gotchas

- `verify.mjs sf` appends `--target-org <session alias>` unless you pass `--target-org`, `--target-org=`, `-o`, `-oX` or `-o=X`. `org list` and `skill install` take no `--target-org`, so run them directly with `node packages/sf-plugin/bin/run.js electivus <cmd>`, with cwd set to the session workspace, and save their stdout yourself. Through the wrapper, `org list` exits 2.
- `--linked` goes before `--`: `verify.mjs sf --linked -- <args>`. After `--` it is passed to `sf electivus` as an argument.
- The command runs with the session workspace as cwd, so `apexlogs/` paths in results point into the session workspace, not the repo. On macOS the results start with `/private/var/…` while `session.workspacePath` starts with `/var/…`: compare real paths, not strings.
- `tooling get --path sobjects/ApexLog/<id>`, without the leading `/`, fails with `Failed to parse URL from sobjects/ApexLog/<id>` (exit 10), although the flag's help says "Relative Tooling API path".
- `log delete`, `trace-flag apply/remove` and `debug-level create/update/delete` preview by default. Without `--yes`, or with `--dry-run`, valid input returns `status: "success"` with `dryRun: true` and does not change the selected Salesforce records. Preview can authenticate and query the org; the verify wrapper still writes its evidence file. `log sync` writes the local store immediately, and `log read` and `log triage` can fetch and cache missing bodies. `skill install` writes unless you pass `--dry-run` and reports `status` per installation. `custom-log capture` has no preview and spends the org's daily event allocation. Keep org mutations to the harness scratch.
- `verify.mjs sf` never contacts the host, so it does not reset the 30-minute idle timer. In a CLI-only stretch, run `node $V doctor` now and then, or start with `--idle-minutes 60`.
- A CLI rebuild needs no session restart, because each call starts the plugin fresh, also through `--linked`.
- For CLI-only regression coverage without VS Code, use `pnpm run test:e2e:cli`. It runs `bin/run.js`, not the plugin inside `sf`.
