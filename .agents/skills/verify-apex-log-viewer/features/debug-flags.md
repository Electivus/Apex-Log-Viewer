# Debug Flags

The Apex Debug Flags editor tab manages trace flags and debug levels in the selected org. A user picks a target (an active user, or a special target such as Automated Process or Platform Integration), a log type (`DEVELOPER_LOG` by default, or `USER_DEBUG`), a debug level and TTL, and then applies or removes the flag of that type. In the debug level manager below, the user can create, edit, preset and delete debug levels. The editor is a single tab: opening it again reveals the open one.

## Sub-features

- `flags-org` selects the org with `debug-flags-org-select`. Opened from Tail, the editor starts on Tail's org.
- `flags-target-user` searches users with `Find user` (`debug-flags-user-search`) and selects a row (`debug-flags-user-row-<userId>`). The org's authenticated user is the first row, with a `You` badge (`debug-flags-you-badge`), even when more than 50 users sort before them by name. The special targets sit under the list.
- `flags-target-special` selects `Automated Process` or `Platform Integration` (`debug-flags-special-target-*`). `debug-flags-status-resolved-count` and `debug-flags-status-active-count` (`0/N`) count the matched users. When the org lacks one, the panel shows `debug-flags-target-unavailable` and disables Apply and Remove.
- `flags-log-type` switches the `Log type` select (`debug-flags-log-type`) between `Developer log (DEVELOPER_LOG)` and `User debug (USER_DEBUG)`. The two are independent TraceFlag records, so switching re-reads the status of the selected target for the new type. The long explanation is behind the `About log types` disclosure (`debug-flags-log-type-help`, a `<details>`).
- `flags-other-log-type` shows `debug-flags-other-log-type-note` inside `CURRENT STATUS` in two cases. With `USER_DEBUG` selected and an active `DEVELOPER_LOG` flag on the target, a warning note says `A DEVELOPER_LOG trace flag is also active on this target until <date>. Salesforce writes each transaction's log at that flag's debug level, so this USER_DEBUG level does not apply until then.` It shows whether or not a `USER_DEBUG` flag exists. With `DEVELOPER_LOG` selected, no active `DEVELOPER_LOG` flag and an active `USER_DEBUG` flag, an info note says `A USER_DEBUG trace flag is active on this target until <date>.`, and `debug-flags-other-log-type-switch` (`Show USER_DEBUG flag`) switches `Log type` to `USER_DEBUG`. Special targets say "on N of M matched targets". No note appears in any other case, nor while the status loads.
- `flags-apply` sets a debug level (`debug-flags-debug-level`) and `TTL (minutes)` (`debug-flags-ttl`, default 30), then clicks `debug-flags-apply`. `debug-flags-notice` says `Debug flag created successfully.` or `Debug flag updated successfully.`, and `CURRENT STATUS` shows the `debug-flags-status-pill` `Active`, `debug-flags-status-level` and `debug-flags-status-expiration`. A TTL outside 1-1440 shows `Default is 30 minutes. Allowed range: 1-1440.` in `debug-flags-error`. On a special target the notice says `Applied debug flags to N matched targets (C created, U updated).` and the expiration reads `-`. The actions sit in a bar pinned to the bottom of the right column, so Apply stays on screen in a short editor. With no target or no debug level it is disabled and `debug-flags-apply-hint` says why.
- `flags-remove` clicks `debug-flags-remove`, which deletes every flag of the selected type on the target, expired ones included. The notice says `Debug flag removed successfully.`, `Removed N <type> trace flag records across M matched targets.` on a special target, which takes a few seconds, or `No active <type> trace flag was found for this target.` when there was none. `CURRENT STATUS` then reads `No active <type> trace flag for this target.` with no pill.
- `flags-level-manager` (`debug-level-manager`) opens on the first existing level by name (`ALV_E2E` on a harness scratch), with the `Maximum Trace` preset preselected in `debug-level-preset-select` and its description in `debug-level-preset-description` (`Every category at its highest documented level. Expect large logs.`). `debug-level-manager-new` starts a draft. `debug-level-apply-preset` fills the draft, `debug-level-draft-*` and `debug-level-field-<category>` edit it, `debug-level-save` saves, `debug-level-reset` (`Reset changes`) reverts, and `debug-level-delete` asks `Delete this DebugLevel from the org?` with `debug-level-delete-confirm` / `debug-level-delete-cancel`. `debug-level-manager-select`, `debug-level-preset-select` and `debug-level-field-*` (lower camel case, such as `debug-level-field-apexCode`) are native selects, so use `selectOption`. Notices: `Debug level created successfully.`, `Debug level updated successfully.`, `Debug level deleted successfully.`.
- `flags-clear-logs`: `Clear logs` → `Delete my logs` / `Delete all org logs` opens a modal on `page` (`Delete all Apex logs for the selected org?`), and the result appears in `debug-flags-notice`, for example `Deleted N Apex log(s).`.

## How to get to it (user POV)

- Click the `Debug Flags` button in the Logs panel toolbar.
- Click the `Debug Flags` button in the Tail panel toolbar.

## Driving it with verify steps

Preconditions:

- Baseline from `README.md`.
- The E2E user `alv.debugflags.<orgId>@example.com` exists, or the step can create it. `h.tooling.ensureDebugFlagsTestUser(auth)` handles both and falls back to the current user when the org has no spare license. The apply/remove step requires a target with no `DEVELOPER_LOG` flags, including expired ones. It refuses the seeded current-user fallback before opening the editor rather than deleting the seed flag.

- **Apply and remove from Logs.** Run `node .agents/skills/verify-apex-log-viewer/scripts/verify.mjs run debug-flags-apply-remove`. It applies the level the panel preselects (the current user's active `DEVELOPER_LOG` level) with a 45-minute TTL (`'{"ttlMinutes":N}'`), and returns `ok: true`, `appliedTraceFlag` (id, `debugLevelName`, start and expiration as read from Tooling), `removed: true` and two shots. The applied shot shows `Active` with the level and expiry.
- **Open from Tail.** `const flags = await h.openDebugFlagsFromTail()`. The editor is a singleton, so the helper first closes an open Apex Debug Flags tab (it activates that tab and runs `View: Close Editor`, after un-maximizing the panel if it hides the editor area) and waits until no Debug Flags frame is left; the frame it returns is the one its own click opened. It requires Tail to show the session org, clicks with retries, and fails unless `debug-flags-org-select` shows `session.org.alias`. `h.openDebugFlagsFromLogs()` closes the tab the same way. The `debug-flags-from-tail-control` step proves an intercepted click fails the helper.
- **Log type and notes.** On the E2E user: select `User debug (USER_DEBUG)` (click `debug-flags-log-type`, then `getByRole('option', { name: 'User debug (USER_DEBUG)' })`), apply, then switch back to `DEVELOPER_LOG`: the info note and its switch appear. Click the switch, which selects `USER_DEBUG`. Select `DEVELOPER_LOG`, apply, then switch to `USER_DEBUG`: the warning note appears. Remove both types at the end.
- **Special target.** Click `[data-testid="debug-flags-special-target-automated-process"]`. `debug-flags-selected-target-label` contains `Automated Process`. On a harness scratch both special targets resolve, so Apply stays enabled. Otherwise `debug-flags-target-unavailable` names the target. For the full apply and remove assertion, see `test/e2e/specs/debugFlagsPanel.shared.ts` → `assertSpecialTargetBehavior`.
- **Debug level manager.** Click `debug-level-manager-new` before `debug-level-apply-preset`, or the preset and Save rewrite the selected level (`ALV_E2E`). Fill `debug-level-draft-developer-name` (for example `ALV_VERIFY_<timestamp>`) and `debug-level-draft-master-label`, then click `debug-level-save`. Read it back with `node … sf -- debug-level get --developer-name <name> --json`; `Maximum Trace` gives Validation `INFO`, System and Nba `FINE`, Workflow, Callout, Visualforce and DataAccess `FINER`, and the rest `FINEST`. Delete it afterwards with `debug-level-delete`, then `debug-level-delete-confirm`, and confirm Tooling no longer returns it.
- **Proof.** Pair each UI shot with a read of the org. As a second channel, run `node .agents/skills/verify-apex-log-viewer/scripts/verify.mjs sf -- trace-flag status --user-id <userId> --json`, adding `--log-type USER_DEBUG` when the panel used that type. Its `warnings` appear under the same conditions as the panel's note, with different text (`result.otherLogType` is always there): the CLI's hidden case reads `No active DEVELOPER_LOG trace flag, but a USER_DEBUG trace flag is active on this target until <ISO>. Run with --log-type USER_DEBUG to see it.`.

## Gotchas

- Use `h.openDebugFlagsFrom*()` rather than a raw click. A forced click on either toolbar button can do nothing.
- The notice confirms only the UI request. Always read the TraceFlag back, because the status pill can lag.
- `h.tooling` reads and seeds `DEVELOPER_LOG` flags only (`getUserDebugTraceFlag` included, despite its name). Read a `USER_DEBUG` flag with `sf -- trace-flag status --log-type USER_DEBUG` or a Tooling query.
- The authenticated user carries a seed `DEVELOPER_LOG` flag at `ALV_E2E` for 60 minutes, renewed by `h.seedLog()` at most once every 5 minutes. `debug-flags-apply-remove` refuses that user while any `DEVELOPER_LOG` flag exists. Deleting and recreating a flag does not preserve its identity or dates. Ad-hoc steps must preserve pre-existing flags rather than claim that recreation restores them.
- Remove every trace flag and debug level the step created, of both log types, on the E2E user too. Harness orgs are reused, and `ALV_E2E` is the level the E2E suite expects.
- Status and notes load after the target changes. Wait for `debug-flags-status-*` or the note instead of reading at once, and probe absent elements with `locator.count()`: `innerText()` on an absent element waits the full 60 s step timeout.
- User search queries the org. A newly created user can take seconds to appear, see `h.tooling.waitForDebugFlagsUserSearchAvailability`.
